## REGRAS GLOBAIS DO MODO DOUBLE CHECK ULTRA

1. **NÃO PRESUMA NADA.**  
   Nada é considerado correto só porque “parece”. Você deve **ler o código real** e **confirmar**.

2. **NÃO INVENTE ARQUIVOS NEM ESTRUTURAS.**  
   Se for criar algo novo (arquivo/ pasta), crie de forma explícita, consistente e documentada.

3. **DOUBLE CHECK + TRIPLE CHECK OBRIGATÓRIO:**
   - Para cada conclusão que você tomar, você deve:
     1. Validar com o código.
     2. Revisar sua própria conclusão.
     3. Verificar se existe algum cenário ou fluxo que você não considerou.
   - Se encontrar qualquer dúvida, investigue até ter certeza.

4. **NADA DE GAMBIRRA / “DEIXA ASSIM MESMO”:**
   - Código confuso → refatore.
   - Código duplicado → extraia.
   - Responsabilidades misturadas → separe.
   - Comentários enganosos → corrija ou remova.

5. **NÃO QUEBRE COMPORTAMENTO SEM SABER:**
   - Em qualquer refatoração, o comportamento funcional deve ser mantido ou melhorado.
   - Se você mudar comportamento, documente explicitamente o porquê.

6. **SEMPRE COMPROVE COM TESTES E/OU EVIDÊNCIAS:**
   - Ao afirmar “isso está correto”, você deve:
     - Mostrar onde no código isso é verdadeiro, OU
     - Criar/rodar testes que comprovem.

7. **PADRÃO DE QUALIDADE:**  
   O objetivo é tornar o front-end **compatível com exigência de produção bancária**:
   - Alta confiabilidade
   - Zero vazamento de informação sensível
   - Performance adequada
   - UX clara e consistente
   - Acessibilidade mínima atendida
   - Cobertura de testes adequada

# FASE 3 – CONTRATOS DE API E INTEGRAÇÃO FRONT–BACK

### 3.1. Localizar todas as chamadas HTTP

Procure em todo o `src/`:

- `fetch(`
- `axios.`
- `apiClient`
- qualquer wrapper de HTTP

Para cada chamada:

1. Identifique:
   - URL.
   - Método (GET/POST/etc.).
   - Payload enviado.
   - Cabeçalhos (se houver).
2. Descubra:
   - Qual componente/página disparou essa chamada.
   - O que o front espera receber de resposta.
   - Quais campos da resposta são usados.

### 3.2. Documentar contratos

Crie:

📄 `docs/04_CONTRATOS_FRONT_BACK_SANKOFA.md`

Para cada endpoint consumido:

- Endpoint (URL).
- Método.
- Quem chama (página/componente/hook).
- Payload (campos e tipos).
- Response (campos e tipos).
- Tratamento de:
  - Sucesso.
  - Erros 4xx.
  - Erros 5xx.
  - Timeout.
  - Resposta malformada.

### 3.3. DOUBLE CHECK dos contratos

- Verifique:
  - Se a mesma API é usada de formas diferentes em lugares diferentes.
  - Se o código assume campos que podem não existir.
  - Se existe tratamento para respostas vazias.

Se identificar qualquer risco de “quebrar tudo” ao menor erro de API:

- Você deve **ajustar o código do front**:
  - Checagens de null/undefined.
  - Fallbacks.
  - Mensagens de erro amigáveis.

# FASE 4 – ANÁLISE E CORREÇÃO DOS FLUXOS CRÍTICOS

Para cada fluxo crítico, você deve:

1. Ler todos os componentes envolvidos.
2. Ver como o estado é controlado.
3. Ver como o erro é tratado.
4. Ver como o usuário é informado.
5. Refatorar tudo o que for frágil.

### 4.1. Predição Unitária de Fraude

Checar:

- Formulário:
  - Campos obrigatórios.
  - Tipos corretos.
  - Validações (range, padrões).
- Chamada a `/api/fraud/predict`.
- Tratamento de:
  - Loading.
  - Sucesso.
  - Erro de validação (front e back).
  - Timeout.
  - Backend indisponível.

Se faltarem validações ou feedbacks:

- Implemente:
  - Mensagens de erro por campo.
  - Mensagem global amigável para falha de backend.
  - Loading visível.

### 4.2. Predição em Batch

Checar:

- Upload de arquivo:
  - Tipo aceito.
  - Validação antes de enviar.
- Chamada a `/api/fraud/batch` ou `/api/infrastructure/batch/process`.
- Tratamento de:
  - Lote grande.
  - Lote vazio.
  - Arquivo inválido.
  - Erros de backend.
  - Timeout.

### 4.3. Lista de Transações

Checar:

- Exibição de dados retornados por `/api/transactions`.
- Paginação.
- Filtros.
- Ordenação.
- Empty state.
- Erros de backend (4xx, 5xx).

### 4.4. Métricas de Modelo

Checar:

- Integração com `/api/model/metrics`.
- Campos exibidos.
- Mensagens quando não há métricas.

### 4.5. Observabilidade & Health

Checar:

- Consumo de `/api/health`, `/api/health/detailed`.
- Consumo de `/api/observability/metrics`, `/api/observability/sla`.
- UI de status:
  - Estados OK / Degradado / Falho.
- Polling e refresh manual.

# FASE 5 – UX, ACESSIBILIDADE, SEGURANÇA E PERFORMANCE

### 5.1. UX

Você deve garantir:

- Navegação clara.
- Botões com textos descritivos.
- Feedback imediato:
  - Ao clicar em ações importantes.
  - Ao ocorrer erro.
- Empty states bem pensados:
  - Quando não existem transações, métricas, etc.

Se encontrar:

- Botão “morto”.
- Mensagens genéricas tipo “Erro”.

Você deve:

- Melhorar textos.
- Corrigir usos errados de componentes.
- Ajustar layout, se necessário.

### 5.2. Acessibilidade

Verifique:

- Navegação por teclado.
- Foco visível.
- Labels em inputs.
- Aria tags quando necessário.
- Contraste de cores.

Se precisar:

- Ajuste estilos.
- Adicione atributos.

Registre em:

📄 `docs/05_RELATORIO_ACESSIBILIDADE_SANKOFA.md`

### 5.3. Segurança

Procure explicitamente por:

- Segredos embutidos em código.
- Logs com dados sensíveis.
- Exposição indevida de detalhes de erro.

Testar XSS:

- Onde dados de usuário ou do backend são exibidos na tela.
- Tente injetar HTML/scripts em campos de entrada (se forem realimentados na UI).
- Se houver risco, corrija (escape, sanitização).

Registre em:

📄 `docs/06_RELATORIO_SEGURANCA_FRONT_SANKOFA.md`

### 5.4. Performance

Analise:

- Componentes que renderizam listas grandes.
- Re-renders desnecessários.
- Ausência de memoização quando necessário.
- Carregamento de páginas:
  - Existe lazy loading de rotas/componentes pesados?

Se identificar gargalos:

- Aplique:
  - Paginação/virtualização.
  - `React.memo`, `useMemo`, `useCallback` quando adequado.
  - Lazy loading de rotas/páginas.

Registre em:

📄 `docs/07_RELATORIO_PERFORMANCE_FRONT_SANKOFA.md`
