## 1. CONTEXTO OBRIGATÓRIO QUE VOCÊ DEVE ASSUMIR

O projeto **Sankofa Enterprise Pro** é um sistema de detecção de fraude bancária em tempo real, com:

- Backend em Python (Flask), 21 endpoints REST operacionais.
- Frontend em React (Vite), dashboards completos (KPIs, calibração, auditoria, revisão manual).
- Banco PostgreSQL com milhares de transações reais e fraudes confirmadas.
- Cache com SimpleCache / Redis.
- Motor de ML com Stacking Ensemble (Random Forest, Gradient Boosting, CatBoost, Logistic Regression como meta-learner).
- Engenharia de features avançada (Bahnsen, features temporais, comportamentais, de dispositivo, etc.).
- Componentes avançados: continuous learning, hard rules, explainability, GNN, NLP, transfer learning, federated learning, integrações externas (Hugging Face), etc.

Você deve tratar esse sistema como **um produto bancário crítico**, sujeito a requisitos rígidos de:

- **BACEN**, **LGPD**, **PCI DSS**, **compliance de risco e fraude**,
- **SLA de latência**, **disponibilidade**, **auditabilidade** e **segurança**.

## 2. COMO VOCÊ DEVE TRABALHAR

1. **Leia com extrema atenção todo o documento de especificação de auditoria que está logo abaixo deste texto**:
   - Esse documento começa com:  
     **"🎯 PROMPT ULTRA-RIGOROSO PARA AUDITORIA E TESTE DE MACHINE LEARNING DO PROJETO SANKOFA ENTERPRISE PRO Versão: 1.0..."**
   - Considere este documento como um **CHECKLIST ULTRA-RIGOROSO OFICIAL** com 13 dimensões de auditoria de ML.
   - Você DEVE seguir aquele checklist de ponta a ponta, sem pular etapas, sem simplificar.

2. Além de seguir fielmente aquele checklist, você tem responsabilidades **EXTRA**, de nível DEUS, que vão além da auditoria:

   - **(A) Fotografar o estado atual do sistema de ML**
     - Identificar:
       - Qual é o modelo atualmente em produção.
       - Quais métricas reais ele está entregando (Precision, Recall, F1, PR-AUC, ROC-AUC, KS, etc.).
       - Como estão as métricas por canal (PIX, crédito, débito, etc.), por faixa de valor, por tempo.
       - Qual é a taxa real de fraude capturada versus fraude perdida (FNs) e o nível de falsos positivos (FPs).
     - Entregar uma visão honesta: pontos fortes e fracos reais.

   - **(B) Avaliar profundamente a qualidade dos dados e dos RÓTULOS (labels)**
     - Verificar:
       - Como as fraudes são definidas, confirmadas e registradas (ground truth).
       - Se há delay de confirmação de fraude (chargeback, contestação, etc.).
       - Se há ruído de rótulo (labels errados, inconsistentes, desatualizados).
       - Se o processo de rotulagem é auditável, documentado e confiável.
     - Conclusão:
       - Dizer se as métricas atuais podem ou não ser totalmente confiáveis dado o processo de rotulagem.

   - **(C) Avaliar e melhorar a ENGINE DE FEATURES**
     - Mapear:
       - Todas as principais features utilizadas.
       - De onde vêm (fonte, tabela, campo).
       - Como são calculadas (transformações).
       - A frequência de atualização (real time, batch, etc.).
     - Verificar:
       - Se treino e produção usam a MESMA lógica de features (mesmo código, mesmos parâmetros).
       - Se há risco de skew (training-serving drift).
     - Propor:
       - Novas features de alto impacto para fraude (temporais, por dispositivo, por relacionamento entre contas, perfil por canal, etc.).
       - Simplificações (remover features redundantes, muito correlacionadas, com baixíssimo ganho).
       - Melhorias de normalização, encoding, tratamento de missing e outliers.

   - **(D) Avaliar e melhorar a MODELAGEM**
     - Verificar:
       - Se o modelo atual é realmente o melhor dado os dados.
       - Se houve comparação justa com modelos baseline simples (Logistic Regression, árvore, XGBoost isolado etc.).
       - Se os hiperparâmetros foram de fato otimizados (grid search, Bayesian, Optuna, etc.).
       - Se há calibragem de probabilidade (Platt, isotonic, etc.).
     - Propor:
       - Um conjunto de modelos candidatos (incluindo variações de ensemble, segmentation models, modelos por canal).
       - Experimentos concretos para:
         - Aumentar Recall com mínimo impacto em Precision.
         - Melhorar PR-AUC na faixa de maior valor financeiro.
         - Otimizar thresholds por segmento (canal, faixa de valor, tipo de cliente).
       - Estratégias de rejeição seletiva (“abstain”/“manter humano”) quando a incerteza for alta.

   - **(E) Validar e tornar a AVALIAÇÃO MUITO MAIS ROBUSTA**
     - Exigir:
       - Split temporal (time-based) para evitar data leakage.
       - Métricas por segmentos: canal, região, faixa de valor, horário, tipo de dispositivo.
       - Avaliação por janela de tempo (ex: últimos 30, 60, 90 dias).
     - Simular:
       - Cenários de pior caso (fraude em picos, datas especiais, horários críticos).
       - Volumes maiores (stress test) para avaliar estabilidade de métricas.

   - **(F) Tratar o feedback loop e o continuous learning como ponto CRÍTICO**
     - Verificar:
       - Se o continuous learning pode sofrer feedback poisoning (dados de retreino contaminados).
       - Se apenas labels confiáveis entram no retreino.
       - Se existe botão de emergência para desligar o learning automático.
     - Propor:
       - Políticas de retreino (quando, com quais dados, com quais filtros).
       - Métricas de “saúde” do novo modelo antes de promoção para produção.

   - **(G) Human-in-the-Loop**
     - Analisar:
       - Fluxo completo da fila de revisão manual.
       - SLA de análise dos casos.
       - Como as decisões humanas são registradas e se viram dados de retreino.
       - Riscos de viés humano reforçando viés do modelo.
     - Propor:
       - Regras claras de quando mandar pro humano.
       - Painéis com casos críticos (fraudes perdidas, falsos positivos graves, transações de alto valor).

   - **(H) Segurança de ML, Fairness, LGPD e Governança**
     - Segurança:
       - Avaliar riscos de data poisoning, model inversion, ataques adversariais e abuso de API.
     - Fairness:
       - Medir métricas de fairness por subgrupo (canal, região, tipo de cliente) e identificar possíveis vieses.
     - LGPD/Compliance:
       - Verificar base legal, explicabilidade, mascaramento de dados, retenção, DPIA/jurídico.
     - Governança:
       - Identificar owners técnico e de negócio, com processo formal de aprovação de modelos.

   - **(I) Custo, Performance e Latência**
     - Avaliar:
       - Latência real (p50, p95, p99) em produção.
       - Custo por 1k inferências e custo mensal estimado do modelo.
       - Gargalos de performance (modelo, banco, cache).
     - Propor:
       - Otimizações técnicas (pruning, quantização, distillation, caching inteligente).
       - Ajustes de infra (horizontal scaling, tuning de banco, etc.).
       - Trade-offs custo vs performance explicitamente documentados.

   - **(J) Orquestração, Observabilidade, Runbooks e Operação 24x7**
     - Verificar:
       - Se há monitoramento de métricas de ML, drift, latência e erros.
       - Se existem alertas automáticos para degradação.
       - Se existem runbooks/playbooks escritos para incidentes de ML.
     - Propor:
       - Runbooks detalhados (passo a passo) para incidentes críticos.
       - Melhoria dos painéis de observabilidade, incluindo casos reais.

- **2. Resultado da Auditoria por Dimensão**
  - Para cada dimensão do checklist original (Definição do Problema, Dados, Features, Modelagem, MLOps, Infra, Segurança, Fairness, Governança, Qualidade de Software, Custo/Performance, Latência/Escalabilidade, Integração), mais:
    - Rotulagem e Ground Truth
    - Continuous Learning & Feedback Loop
    - Human-in-the-Loop
    - Runbooks/Operação/DR
  - Indicar:
    - Status (✅/⚠️/❌),
    - Evidências (arquivos, trechos de código, endpoints, métricas),
    - Análise detalhada,
    - Recomendações concretas (com prioridade).

- **3. Matriz de Conformidade**
  - Tabela com todas as dimensões e seus status.

- **4. Plano de Ação para Otimizar MÉTRICAS E QUALIDADE DAS PREDIÇÕES**
  - Lista priorizada de ações:
    - [Alta] Melhorar dado/label em X.
    - [Alta] Ajustar features Y e Z.
    - [Alta] Rodar experimento com modelo M1, M2, M3 para otimizar F1/PR-AUC.
    - [Média] Otimizar thresholds por segmento.
    - [Média] Configurar monitoramento de drift ABC.
  - Para cada ação:
    - O que fazer,
    - Por que fazer,
    - Que ganho esperado em métrica/negócio.

- **5. Conclusão**
  - Se o sistema pode ser considerado:
    - Pronto para produção,
    - Pronto com ressalvas,
    - Ou se precisa de melhorias antes do go-live.
  - Quais métricas devem ser acompanhadas semanalmente / mensalmente.
  - Quando é recomendável fazer uma nova auditoria.
