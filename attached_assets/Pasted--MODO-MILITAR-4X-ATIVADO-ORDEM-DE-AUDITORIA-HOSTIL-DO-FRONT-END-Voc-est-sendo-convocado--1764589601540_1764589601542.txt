🔥 FASE 1 – CHECKLIST MILITAR POR TELA (SEM ESCAPATÓRIA)

Para CADA UMA das telas listadas no contexto (e qualquer outra detectada), você deve construir um CHECKLIST MILIMÉTRICO contendo:

1. Componentes visuais existentes naquela tela:
   - Cards
   - Gráficos
   - Tabelas
   - Inputs
   - Selects
   - Sliders
   - Toggles
   - Abas
   - Botões (primários, secundários, de ação)
   - Ícones clicáveis
   - Badges / status / chips
   - Tooltips
   - Mensagens de estado (vazio, erro, loading, sucesso)

2. Dados esperados para cada componente:
   - Origem dos dados (endpoint / serviço / estado global)
   - Tipo de dado (numérico, texto, porcentagem, monetário, data-hora, enum)
   - Formatação exigida (R$, %, datas, etc.)
   - Estado quando não há dados

3. Ações possíveis:
   - Cliques
   - Filtros
   - Ordenações
   - Paginação
   - Mudança de período (ex: últimas 24h)
   - Abas / categorias
   - Botões “Novo”, “Atualizar”, “Exportar”, “Aplicar mudanças”, etc.

Você DEVE transformar isso em um **PLANO DE TESTE EXPLÍCITO** por tela:  
[ Tela X ] → Lista de componentes, dados, ações e expectativas.

Nenhuma tela pode ficar sem esse mapa.

======================================================================
🔥 FASE 2 – TESTES FUNCIONAIS PROFUNDOS (GUERRA TOTAL)

Para cada item do checklist de cada tela, você deve garantir:

2.1. Teste funcional unitário:
   - Comportamento do componente isolado.
   - Renderização correta com props válidas.
   - Comportamento com props limites e inválidas.

2.2. Teste funcional de integração:
   - Interação entre filtros, tabelas, gráficos e controles.
   - Por exemplo:
     • Na tela de Transações: alterar filtros de status, tipo, período, buscar por CPF, ordenar por “mais recentes” e validar se a tabela responde corretamente.
     • Na Central de Alertas: buscar alertas, filtrar severidades, abrir detalhes e validar estados.

2.3. Teste de estados:
   - Estado inicial (carregando).
   - Estado vazio (sem dados).
   - Estado com dados.
   - Estado de erro (back-end falhando).
   - Estado de reconexão e atualização.

Você DEVE gerar ou reforçar testes automatizados (ex: React Testing Library, Cypress/Playwright ou equivalente), cobrindo explicitamente esses cenários.

======================================================================
🔥 FASE 3 – INTEGRAÇÃO FRONTO ↔ BACK-END SOB FOGO PESADO

Para CADA ação que dependa de dados do back-end, obrigatoriamente:

3.1. Identificar:
   - Qual serviço/cliente HTTP é chamado.
   - Qual endpoint (URL, método).
   - Quais parâmetros são enviados.
   - Qual payload de request.
   - Qual payload esperado de response.

3.2. Validar:
   - Se o endpoint existe de fato no back-end.
   - Se o contrato está alinhado (tipos, nomes de campos, formatos).
   - Se há tratamento para:
     • HTTP 2xx
     • HTTP 4xx
     • HTTP 5xx
     • Timeout
     • Network error
     • Response vazio
     • Response com estrutura incompleta

3.3. PROIBIÇÕES:
   - Uso de mocks em ambiente considerado “real”.
   - Uso de dados hard-coded onde deveria vir do back.
   - Ignorar erros silenciosamente (catch vazio, console.log e segue).
   - Suprimir erros sem feedback ao usuário.

3.4. Você deve gerar uma MATRIZ DE INTEGRAÇÃO:
   - [Tela] → [Ação] → [Endpoint] → [Contrato] → [Tratamento de sucesso] → [Tratamento de erro]

Qualquer divergência → classificar como FALHA CRÍTICA.

======================================================================
🔥 FASE 4 – RESILIÊNCIA, ESTADOS LIMITE E COMPORTAMENTO EM SITUAÇÃO DE CRISE

Simule (conceitualmente e em testes) cenários extremos:

4.1. Carga alta:
   - Muitas transações sendo exibidas.
   - Muitos alertas simultâneos.
   - Muitas investigações ativas.
   - Uso intensivo de filtros e paginação.

4.2. Back-End instável:
   - Endpoints lentos.
   - Respostas intermitentes.
   - Parte das APIs fora do ar.

4.3. Dados “malformados” ou inesperados:
   - Nulos em campos que normalmente vêm preenchidos.
   - Strings onde deveriam ser números.
   - Valores fora de faixa (ex: % > 100).

Você DEVE:
- Verificar se o front quebra.
- Verificar se há fallback amigável.
- Verificar se o usuário vê mensagens claras e úteis.
- Propor correções de código caso o comportamento não seja robusto.

======================================================================
🔥 FASE 5 – COBERTURA DE TESTES EM MODO DE COMBATE

Seu objetivo NÃO é apenas dizer “faça testes”.  
Seu objetivo é **DEFINIR e/ou GERAR** um arcabouço de testes completo, incluindo:

5.1. Testes unitários:
   - Para componentes básicos (cards, tabelas, gráficos, filtros).
   - Para componentes complexos (calibragem, dashboards, listas VIP/HOT, trilhas de auditoria).
   - Para helpers/utilitários relacionados a formatação (datas, moeda, %).

5.2. Testes de integração:
   - Fluxos de tela completa (ex: “Calibrar modelo”, “Criar regra”, “Adicionar VIP/HOT”, “Salvar configurações do sistema”).
   - Interações entre componentes de filtros + tabelas + gráficos.

5.3. Testes E2E:
   - Caminhos críticos em produção:
     • Abertura da aplicação.
     • Navegar pelo menu principal entre as telas.
     • Calibrar o motor e aplicar mudanças.
     • Ver monitoramento e métricas em tempo real.
     • Criar/editar regras rígidas.
     • Gerenciar listas VIP/HOT.
     • Ver trilhas de auditoria.
     • Configurar sistema, banco, segurança, IA & ML e API.
   - Verificação de que essas operações refletem corretamente no back-end.

Requisito militar:
- A cobertura deve ser **alta e significativa**, evitando testes triviais e irrelevantes.
- Você deve apontar onde a cobertura está fraca e propor exatamente quais testes faltam.

======================================================================
🔥 FASE 6 – SEGURANÇA E COMPLIANCE VISÍVEIS NO FRONT-END

Você deve buscar de forma agressiva:

6.1. Vazamento de dados sensíveis:
   - Tokens, chaves, secrets, IDs críticos.
   - Dados de clientes, CPFs, informações sensíveis sendo logadas ou exibidas sem necessidade.

6.2. Possíveis brechas:
   - Falta de validação de entrada.
   - Inputs sem sanitização.
   - Possível XSS (dados não escapados).
   - Possíveis problemas relacionados a CORS/CSRF (no que couber ao front).

6.3. Coerência com as telas de segurança:
   - Se a tela de “Configurações de Segurança” mostra opções de 2FA, SSL, logs de auditoria etc., você deve verificar se:
     • As opções realmente persistem.
     • As configurações são refletidas em comportamento real.
     • Não são "placeholders" desconectados do back-end.

Qualquer inconsistência deve ser classificada como RISCO OPERACIONAL.

🔥 FASE 7 – UX, ACESSIBILIDADE E CONSISTÊNCIA VISUAL

Validar agressivamente:

7.1. Consistência de:
   - Cores, ícones, espaçamentos, tipografia, estilos de botões.

7.2. Acessibilidade:

   - Aria-labels em ícones de ação.
   - Textos alternativos quando necessário.

7.3. Experiência:

   - Existem mensagens claras quando não há dados?

Se encontrar pontos confusos ou inconsistentes, você deve:
- Explicar o problema.
- Sugerir melhorias concretas.
- Se possível, sugerir ajustes de código/markup.
