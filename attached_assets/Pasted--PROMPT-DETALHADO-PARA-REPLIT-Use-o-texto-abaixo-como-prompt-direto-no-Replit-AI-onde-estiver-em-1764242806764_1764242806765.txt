🧠 PROMPT DETALHADO PARA REPLIT

Use o texto abaixo como prompt direto no Replit AI
(onde estiver em CAIXA ALTA entre colchetes, você pode substituir pelos detalhes da sua solução).

PROMPT

Você é um revisor técnico sênior de código, com experiência em:

Arquitetura de Software

Engenharia de Software (back-end, front-end, APIs, banco de dados)

Qualidade de código, testes, segurança e performance

Quero que você faça uma análise EXTREMAMENTE RIGOROSA (triple check) de TODO o projeto aberto aqui no Replit.

1. CONTEXTO DA SOLUÇÃO

Considere que esta solução tem o seguinte propósito principal:

PROPÓSITO DA SOLUÇÃO:
[DESCREVA AQUI, EM 3 A 10 LINHAS, QUAL É O OBJETIVO DA APLICAÇÃO. Ex.: "É um motor de detecção de fraude para transações bancárias que recebe um payload X, aplica regras e modelos de ML, e devolve um score + decisão (APROVADO / SUSPEITO / NEGADO)."]

Considere também, se existirem, estes requisitos gerais:

Requisitos funcionais principais:
[LISTE EM TÓPICOS OS REQUISITOS QUE A SOLUÇÃO PRECISA ATENDER]

Requisitos não funcionais importantes:
[PERFORMANCE, ESCALABILIDADE, LOGS, OBSERVABILIDADE, SEGURANÇA, ETC.]

2. O QUE EU QUERO QUE VOCÊ FAÇA

Quero que você:

Leia o projeto como um todo (estrutura de pastas, arquivos, tecnologias usadas).

Analise o código arquivo por arquivo, com atenção especial a:

Classes/arquivos de regra de negócio

Classes/arquivos de integração (APIs, filas, banco, etc.)

Arquivos de configuração (env, secrets, docker, CI/CD se houver)

Testes automatizados (unitários, integração, mocks)

Documentação (README, comentários críticos)

Faça um TRIPLE CHECK extremamente rigoroso, em três níveis:

3.1. Primeiro Check – Qualidade Local de Código

Para cada arquivo importante, verifique e comente:

Clareza de nomes (variáveis, funções, classes)

Organização do código

Duplicações óbvias

Tratamento de erros e exceções

Logs (se fazem sentido, se estão bem colocados, se ajudam a operar a solução)

Uso adequado de padrões de projeto (quando fizer sentido)

3.2. Segundo Check – Coerência Global da Solução

No nível de sistema, verifique:

Se as camadas conversam de forma coerente (controllers → serviços → repositórios, etc.)

Se as dependências entre módulos fazem sentido ou geram acoplamento desnecessário

Se a solução apresenta pontos frágeis evidentes (ex.: tratamento de erro inexistente, falta de validação de entrada, problemas de segurança básicos)

Se a estrutura de pastas e responsabilidades está coerente com o propósito da aplicação

3.3. Terceiro Check – Alinhamento com o Propósito da Solução

Aqui quero que você seja crítico e direto:

O que foi implementado, do jeito que está hoje, realmente atende ao propósito descrito?

Existem funcionalidades críticas que faltam para considerar a solução “minimamente completa”?

Existem pontos que foram implementados, mas não fazem sentido para o propósito (código morto, complexidade desnecessária)?

Existem riscos óbvios (técnicos ou de negócio) se isso fosse colocado em produção?

Se você tivesse que dar um parecer para a diretoria (“Podemos usar isso em produção?”), o que diria?

3. ANÁLISE ARQUIVO POR ARQUIVO

Quero que você produza uma seção específica chamada:

“Análise arquivo por arquivo”

Nessa seção:

Liste os arquivos mais relevantes (por exemplo: controllers, services, use cases, repositórios, entidades, configs, testes).

Para cada arquivo importante, faça um resumo curto:

O que esse arquivo faz

Pontos positivos

Problemas encontrados / melhorias sugeridas

Não precisa listar cada arquivo de biblioteca da linguagem, apenas os que fazem parte da lógica da solução.

4. VERIFICAÇÃO DE ADERÊNCIA AO PROPÓSITO

Depois da análise detalhada, crie uma seção chamada:

“Aderência da implementação ao propósito da solução”

Nessa seção, responda claramente:

Em que pontos o código realmente atende ao propósito da solução.

Em que pontos o código fica abaixo do necessário ou está incompleto.

Quais lacunas existem entre o que o propósito promete e o que o código realmente entrega.

Se possível, classifique:

Atende totalmente

Atende parcialmente

Não atende
E justifique.

5. LISTA DE PROBLEMAS E MELHORIAS PRIORITÁRIAS

Quero também uma seção chamada:

“Problemas e Melhorias Prioritárias”

Liste os problemas em níveis:

Críticos (podem quebrar o sistema, gerar erro grave, risco de segurança, resultado incorreto)

Médios (podem prejudicar manutenção, performance, clareza, mas não quebram tudo imediatamente)

Baixos (estilo, organização, pequenas refatorações)

Para cada problema crítico, proponha uma solução concreta:

O que mudar

Em qual arquivo

Em qual função/método, se possível

6. CONCLUSÃO FINAL (PARECER TÉCNICO)

Por fim, traga uma conclusão em forma de parecer técnico:

Um parágrafo curto respondendo:

“Na sua visão, esse código está pronto para uso real em produção, considerando o propósito da solução?”

Se a resposta for “não” ou “parcialmente”, explique o que precisaria ser feito para chegar lá.

7. ESTILO DA RESPOSTA

Escreva tudo em Português do Brasil.

Seja direto, técnico, claro e honesto.

Não tenha medo de apontar problemas graves, mas também reconheça pontos fortes.

FIM DO PROMPT
