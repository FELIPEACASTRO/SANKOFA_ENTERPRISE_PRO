### 2.3. Saída obrigatória:

# 3. INTEGRAÇÃO COM BACKEND – VERIFICAÇÃO + CORREÇÃO

Mapeie todas as chamadas HTTP:

- Localize todos os `fetch`, `axios`, `apiClient` etc.
- Liste para qual endpoint cada chamada vai.
- Verifique, para cada endpoint:

  1. **Request**:
     - Payload enviado.
     - Tipos dos campos.
     - Headers (se houver).
  2. **Response**:
     - Estrutura esperada.
     - Campos que o código de front utiliza.
     - Tratamento de cenários:
       - 200 OK com dados.
       - 4xx (erro de validação/negócio).
       - 5xx (erro interno).
       - Timeout.
       - Response malformada.

Se houver qualquer fragilidade:

- Falta de tratamento de erro → implemente try/catch e fluxo de erro apropriado.
- Ausência de loading state → implemente.
- Erro só com `console.log` → substitua por mensagem amigável na UI + log controlado.

Crie um arquivo:

`docs/CONTRATOS_FRONT_BACK_SANKOFA.md`

Com a tabela:

- Endpoint.
- Componente que chama.
- Payload.
- Response.
- Tratamento de erro.
- Comentários.

# 4. FLUXOS CRÍTICOS – EXERCITAR E FORTALECER

Para cada fluxo core, você deve garantir que o código:

- Está correto.
- Está legível.
- Está robusto.
- Tem testes.

### 4.1. Fluxo: Predição Unitária (`/api/fraud/predict`)

Verifique:

- Tela de formulário.
- Validação de campos:
  - Campos obrigatórios.
  - Tipos numéricos.
  - Ranges.
- Estados:
  - Antes do envio.
  - Durante (loading).
  - Após (resultado).
- Uso da resposta:
  - `is_fraud`.
  - `risk_score`.
  - Explicações (fatores de risco/proteção, texto, flags LGPD).
- Comportamento em:
  - Falha de validação no front.
  - Falha no backend 4xx.
  - Falha 5xx.
  - Timeout.

Se algo estiver faltando, implemente.

### 4.2. Fluxo: Predição em Batch (`/api/fraud/batch` / `/api/infrastructure/batch/process`)

Verifique:

- Upload de arquivo.
- Tipo de arquivo aceito.
- Validações.
- Feedback durante o processamento.
- Resultado exibido.
- Comportamento em caso de:
  - Arquivo inválido.
  - Arquivo muito grande.
  - Erros da API.

### 4.3. Fluxo: Lista de Transações (`/api/transactions`)

Verifique:

- Tabela.
- Paginação.
- Filtros.
- Ordenação.
- Empty state.
- Erros.

### 4.4. Fluxo: Métricas (`/api/model/metrics`)

Verifique:

- Exibição dos dados.
- Consistência visual.
- Tratamento de erros.

### 4.5. Fluxo: Observabilidade & Health

Verifique:

- Consumo de `/api/health`, `/api/health/detailed`.
- Consumo de `/api/observability/metrics`, `/api/observability/sla`.
- Interface:
  - Indica claramente quando está tudo ok?
  - Indica claramente quando está degradado?
  - Se o backend cair, a UI continua funcionando (avisando o usuário)?

Para cada fluxo, se necessário:

- Ajuste layout.
- Ajuste textos de feedback.
- Adicione estados de loading/erro.

Você deve:

- Garantir que todas as telas:
  - Tenham títulos claros.
  - Tenham botões claros (texto objetivo, sem ambiguidades).
  - Tenham feedback visual no clique (ou loading).
- Garantir que:
  - Não existam telas “mortas” ou sem saída.
  - Não existam elementos clicáveis que não façam nada.

Se encontrar:

- Botão sem ação → implemente ou remova.
- Textos confusos → melhore a copy.
- Layout quebrado → ajuste o CSS/estilos.

# 7. SEGURANÇA NO FRONT-END

Você deve buscar ativamente por:

- Segredos expostos.
- URLs sensíveis hard-coded (aceitável só se forem internas).
- Logs com dados sensíveis.
- Trechos de código que exibem erros internos de forma crua.

Você deve:

- Remover console.log sensíveis.
- Trocar mensagens internas por mensagens amigáveis.
- Garantir que qualquer dado sensível que apareça na UI esteja lá por design, nunca por vazamento.

Testar XSS básico em pontos onde há entrada do usuário ou renderização de texto vindo da API:

- Se identificar risco, ajustar para escapar conteúdo.
